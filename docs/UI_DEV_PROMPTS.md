# PyQt6 / GUI 项目通用 Prompt 模板

> 适用：PyQt6 / Tkinter / Web 前端项目
> 用法：每段对应 GUI 开发的一个阶段，按顺序使用

---

## 模板 A：UI 设计阶段

```
# UI 组件设计阶段

## 任务

设计 [模块名] 的 UI 组件，先列计划，不写代码。

## 必须遵守的"用户视角设计原则"

每个 UI 元素必须明确定义：
1. **视觉状态**：默认 / hover / 点击 / 禁用 / loading / 错误
2. **触发动作**：点击后**发生什么具体可见的事**（不能是"调用 xxx 函数"，要是"按钮变灰 + 文字变 'Processing...'"）
3. **反馈机制**：用户怎么知道动作"完成了"（弹窗 / 状态栏文字 / 进度条 / 颜色变化）
4. **失败处理**：动作失败时用户看到什么（错误弹窗内容 + 是否可重试）

## 必须列出的清单

对每个组件回答：

| 组件 | 视觉位置 | 触发动作 | 完成反馈 | 失败反馈 | 禁用条件 |
|---|---|---|---|---|---|
| [按钮 X] | 右上 | ... | ... | ... | ... |

## 严禁

- "占位"组件（创建了但没逻辑）
- "TODO"标记（要么不做要么做完）
- 假设用户会"按预期顺序"操作（用户会乱点）
- 单一路径思维（必须考虑：用户没选图就点检测？用户点 N 次取消？）

## 阶段 1 输出

markdown 表格 + 5 个"非预期用户操作"的应对方案，让我审查。
```

## 模板 B：UI 实现阶段

```
# UI 组件实现阶段

## 任务

实现 [模块名]。基于阶段 1 已 review 通过的计划。

## 必须做的事

1. 每个 widget 创建后**立即绑定 signal/slot**（不能只创建不连接）
2. 每个按钮的 onClick 必须有**具体函数**实现（不能是 lambda: print('TODO')）
3. 每个 dialog 必须有**关闭路径**（x 按钮 + Esc 键 + 取消按钮 至少 2 个）
4. 每个长操作必须有**视觉反馈**（loading 指示 / 进度条 / 禁用相关按钮）
5. 每个异常路径必须有**用户可见的提示**（不能 print 到终端）

## 自检清单（写完代码后必须自己跑一遍）

写完代码后，**用 grep 检查以下"代码气味"**：

\`\`\`bash
# 1. TODO/FIXME（必须 0 个）
grep -rn "TODO|FIXME|XXX" src/

# 2. 空 callback（必须 0 个）
grep -rn "pass$|...$|lambda:.* None|lambda:.* pass" src/

# 3. 异常静默吞噬（必须 0 个）
grep -rn "except.*: *$|except.*: *pass|except Exception: *$" src/

# 4. 第一人称（README 等公开文档不应有"我"）
findstr /i "我做|我实现|我设计" README.md

# 5. 调试用 print（生产代码不应有）
grep -rn "print(" src/ | grep -v test_
\`\`\`

每条命令的输出必须是空，否则报告每条非空的位置。

## "假装我是用户"自测清单

写完代码后**必须自己当用户跑一遍**，对每个 button / menu / dialog：

[ ] 点击它，看到了什么？（不是"调用了 xxx"，是"界面发生了什么"）
[ ] 在错的时机点它（没数据时点保存？正在跑时点开始？）会怎样？
[ ] 在正确时机点它，反馈在哪里看到？多久看到？
[ ] 失败时看到什么？错误信息是否清晰？
[ ] 重复点击 5 次会怎样？

如果 5 个问题里**任何一个回答不出来**，说明实现不完整，必须补。

## 报告要求

完成后报告：

1. 自检 5 条 grep 结果（每条都应该是空）
2. 每个组件的 5 个"假装用户"测试问答
3. **如果有任何一个组件你没法亲自点击测试**（比如 dialog 你只能跑代码不能看效果），明确说出来让我手动测
```

## 模板 C：UI 验收阶段

```
# UI 组件验收阶段

## 任务

[模块名] 代码已完成，需要做"用户视角验收"。

## CC 必须做的

按以下顺序：

1. **代码级验收**（你可以做）
   - 全部 widget 创建 OK：grep "QPushButton|QLabel..." 看清单是否齐全
   - 全部 signal 已 connect：grep "connect|emit" 找出未连接的 signal
   - 全部 callback 非空：检查没有 pass / lambda: None

2. **行为级验收**（你**不能做**，必须让用户做）
   你不能点击按钮，不能看 dialog 弹出来的样子。
   所以你**必须**给用户一份"手动验收清单"。

## 用户验收清单要求

清单格式：
[ ] 启动应用 → 看到什么？（具体的视觉描述）
[ ] 点击 [按钮 X] → 应该发生 [Y]
[ ] 在错的时机点 [按钮 X] → 应该看到 [Z 警告]
[ ] [失败场景] → 应该弹出 [W 错误]
[ ] 关闭应用 → 进程是否退出？

每条清单包含：
- **具体操作步骤**（不是"测试 X 功能"，是"点 X 按钮"）
- **预期结果**（具体可见的现象）
- **失败标志**（如果你看到 A 而不是 B，说明 bug）

## 严格禁止

- 自己声称"功能 OK"而没有用户验证清单
- 用"看起来应该没问题"代替实际清单
- 跳过失败路径（不能只测"正常流程"）

## 输出

完整的用户验收清单（10-20 项），编号、操作、预期、失败标志，markdown 表格格式。
```

## 模板 D：UI bug 修复阶段

```
# UI bug 修复阶段

## 任务

用户验收发现 bug：[描述 bug 现象]

## CC 必须做的

1. **优先理解 bug 本质，不要立即写修复**
   - 这是 UI 渲染问题？还是逻辑问题？还是数据问题？
   - 这是 CC 当初没实现的功能？还是实现错了？
   - 这是 widget 没绑定？还是绑定了但 callback 错？

2. **给出 3 种修复方案**
   不是直接给一种"最好的"修复——给 3 种：
   - 方案 A：最小改动（5 行代码内）
   - 方案 B：标准修复（10-30 行）
   - 方案 C：彻底重写（30+ 行）

   对每种方案：
   - 列出改动的具体行号
   - 列出潜在风险（会不会引入新 bug？）
   - 列出"如果选这个方案，需要重新验证什么"

3. **等用户选定方案后再实施**

## 严格禁止

- 自作主张选方案
- "顺便"修其他没要求的 bug
- 跳过"为什么"的解释（必须先说清楚为什么 bug 发生）
```

## 项目通用检查清单

### 设计阶段必查

- [ ] 每个 widget 的 5 种状态（默认/hover/点击/禁用/loading）都定义了
- [ ] 每个长操作的进度反馈方式定义了
- [ ] 每个失败路径的错误提示定义了
- [ ] "用户在错的时机操作"的应对定义了

### 实现阶段必查（grep 自检）

- [ ] `grep -rn "TODO|FIXME" src/` → 输出为空
- [ ] `grep -rn "lambda:.* pass|pass$" src/` → 输出为空（或注释清楚）
- [ ] `grep -rn "except.*: *$|except.*: *pass" src/` → 输出为空
- [ ] `grep -rn "print(" src/` → 检查是否应该改成 logger

### 验收阶段必查（亲自操作）

- [ ] 每个按钮点击后视觉反馈在多少 ms 内出现（应 < 100ms）
- [ ] 每个长操作是否能取消
- [ ] 取消操作的延迟（应 < 200ms）
- [ ] 关闭应用后任务管理器无残留进程
- [ ] 应用启动到可交互的时间（应 < 5s）
- [ ] 所有菜单点击都能展开 / 关闭

### 截图必查

- [ ] 启动后的干净截图（无任何检测结果）
- [ ] 每个核心功能的成功截图
- [ ] 长操作进行中的截图（含进度反馈）
- [ ] 错误状态的截图（手动触发一个错误，看 UI 怎么反应）

### 上线前必查

- [ ] README 中的数字 = 截图中的数字（不矛盾）
- [ ] 所有截图的 path 一致（不要左截图说 1440，右截图说 1800）
- [ ] 简历中的卖点 = 代码实测数据（不夸大）
